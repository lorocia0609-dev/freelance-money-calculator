# Internationalization (EN/ES)

Two locales double the addressable market for a tool that computes the same
numbers either way. It only pays off if the Spanish pages are genuinely Spanish —
translated slugs, translated copy, correct formatting — rather than an English
site with swapped labels.

Retrofitting i18n is the most expensive avoidable rework in this stack: it
touches every component and, because URLs change, it forfeits accumulated
rankings. Build it in from the first page even while only one locale has content.

## Routing

- Locale prefix on every route: `/en/...` and `/es/...`.
- Prefix the default locale too. A mix of prefixed and unprefixed routes creates
  duplicate-content ambiguity and awkward special cases in link building.
- The root `/` resolves to the default locale. Language detection may *suggest* a
  switch, but must never silently redirect: a crawler or a user arriving from a
  shared link must land on the URL they requested.
- Slugs are translated per locale, from `registry.ts`. A Spanish page on an
  English slug will not rank in Spanish-language search.

## Translation catalogues

- One JSON file per locale in `src/i18n/`, keys namespaced by tool id.
- Look keys up through a helper that throws (or loudly warns) on a missing key in
  development. Silent fallback to the default locale is how half-translated pages
  reach production unnoticed.
- Keep the catalogues structurally identical across locales; a key present in one
  and absent in another is a bug worth failing the build over.
- Never concatenate translated fragments — grammar and word order differ. Use
  parameterized strings: `"resultSummary": "You should charge {rate} per hour"`.
- Pluralization goes through `Intl.PluralRules`, not `count === 1 ? ... : ...`.

## Formatting

Always format through `Intl`, never by hand:

```ts
new Intl.NumberFormat(locale, { style: 'currency', currency }).format(value);
```

Manual formatting gets decimal separators, thousands separators and symbol
placement wrong for at least one of the two locales — Spanish and English
disagree on all three.

## Currency architecture

Keep currency independent of locale. They are different axes: a Spanish speaker
may work in USD, an English speaker in EUR.

- Store a currency code (ISO 4217) in state, defaulting per project convention.
- Let `Intl` derive symbol, placement and decimal precision from the code.
- Do **not** convert between currencies. Conversion needs live rates, which means
  an external API — a dependency, a rate limit and eventually a bill. The tool
  computes in whichever currency the user enters; make that explicit in the copy.

## hreflang

Every locale variant lists every other, plus `x-default`:

```html
<link rel="alternate" hreflang="en" href="https://example.com/en/hourly-rate-calculator/" />
<link rel="alternate" hreflang="es" href="https://example.com/es/calculadora-tarifa-hora/" />
<link rel="alternate" hreflang="x-default" href="https://example.com/en/hourly-rate-calculator/" />
```

Links must be reciprocal and absolute. Non-reciprocal hreflang is ignored
entirely, which is why the audit script checks it on the built output rather
than trusting the source.

## Language switcher

The switcher navigates to the *equivalent page* in the other locale, not to that
locale's homepage — dropping a user on the homepage loses their context and
increases bounce. Resolve the target through the registry. Preserve the query
string so the switch does not discard the values they just entered.

## Content parity

Both locales get real content. When translation lags, it is better to publish
fewer tools in both languages than more tools in one — a partially translated
site trains search engines to distrust the whole hreflang cluster.
